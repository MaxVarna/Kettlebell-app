# Слой БД каталога упражнений

Реляционное хранение справочника гиревых упражнений для сервиса `content`.

Источник истины — продуктовый контракт `docs/EXERCISE_DATA_MODEL.md` (`ExerciseRecord`, `schemaVersion: 2`). Схема хранит этот контракт без потери данных и собирает из него готовую клиентскую запись.

## Файлы

- `schema.sql` — DDL (PostgreSQL): ENUM-типы, ядро упражнения, фазы с male/female ассетами, структурированные источники с привязкой к утверждениям, версии публикаций, редакторский слой, а также функции экспорта и публикации.
- `seed_example.sql` — эталонное упражнение «двуручный мах».
- `seed_reference_data.sql` — справочники без демонстрационного упражнения; используется кандидатами и генератором.
- `candidates/index.json` — явный список упражнений, разрешённых для клиентского экспорта.
- `candidates/*.sql` — проверяемые карточки-кандидаты.
- `SCHEMA.md` — соответствие полей контракту, ключевые решения, условия публикации.
- `test_export.py` — тест детерминизма экспорта.
- `test_candidate_deadlift.py`, `test_candidate_swing.py` — проверки реальных опубликованных кандидатов.
- `requirements-test.txt` — зафиксированная зависимость теста (`pgserver==0.1.4`).
- `../scripts/generate_mobile_catalogue.py` — экспорт утверждённых записей и Metro-манифеста.

## Границы

Ядро содержит только продуктовую модель упражнения — без веса, повторов, подходов, раундов, дистанции и темпа. Универсальная классификация, дисциплины, теги, каталог мышц и связи упражнений — редакторский слой, в клиентскую запись не экспортируется.

## Экспорт и публикация

- `fn_export_exercise_record(id)` → `ExerciseRecord` (jsonb, `schemaVersion: 2`)
- `fn_publication_checklist(id)` → 8 правил публикации с результатом
- `fn_can_publish(id)` → boolean
- `fn_publish_exercise(id, by)` → пишет иммутабельный снимок записи и возвращает номер версии

## Формат дат

Экспорт дат детерминирован и не зависит от `TimeZone` сессии: `review.reviewedAt` отдаётся в UTC ISO 8601 с суффиксом `Z` (напр. `2026-07-22T10:00:00Z`), `sources[].accessedAt` — как `YYYY-MM-DD`. Приведение к UTC зашито в `fn_export_exercise_record`, а не берётся из настройки сессии.

## Проверка

Схема прогнана на реальном PostgreSQL: DDL и seed применяются без ошибок, экспорт даёт запись строго по контракту, все 8 условий публикации проходят, версия-снимок пишется, а нарушение любого правила корректно блокирует публикацию. `test_export.py` проверяет, что при двух РАЗНЫХ применённых зонах экспортированный `ExerciseRecord` идентичен, а `reviewedAt` оканчивается на `Z`.

Тест устойчив к ложноположительному результату. `pgserver.psql()` не включает `ON_ERROR_STOP` и теряет `stderr`: ошибочный `SET TIME ZONE` там игнорируется, `COPY` всё равно выполняется, и прогон раньше проходил ложно. Поэтому тест запускает `psql` сам, с `\set ON_ERROR_STOP on` и захватом `stderr` — любая SQL-ошибка роняет прогон с понятной диагностикой (без traceback), а фактически применённая зона сверяется через `current_setting('TimeZone')`. Основной прогон использует переносимые числовые смещения `SET TIME ZONE 0` и `SET TIME ZONE 3` (не требуют базы именованных зон). Именованная `Europe/Sofia` вынесена в необязательную интеграционную проверку: на полноценной установке PostgreSQL она сверяет идентичность записи, а на встроенном сервере без tz-базы помечается как SKIP.

Тест использует встроенный PostgreSQL из пакета `pgserver` (колёса под Windows `win_amd64`, macOS и Linux, Python 3.9–3.12) — отдельный сервер ставить не нужно. Зависимость ставится в виртуальное окружение, `--break-system-packages` не используется.

Windows (PowerShell / cmd):

```
cd services\content\db
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements-test.txt
python test_export.py
```

macOS / Linux:

```
cd services/content/db
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-test.txt
python test_export.py
```

Коды выхода теста: `0` — пройден; `1` — упал (несовпадение JSON/формата даты либо SQL-ошибка в прогоне при `ON_ERROR_STOP`); `2` — не установлен `pgserver` (тест печатает инструкцию по установке, а не traceback); `3` — окружение не готово: не нашёлся ASCII-каталог либо упал `initdb`/запуск PostgreSQL (печатается диагностика, не traceback).

### Windows с кириллицей в профиле

Штатный `pgserver` вызывает `initdb` с `--encoding=utf8`, но без `--locale`, и берёт каталог данных из `%TEMP%`. На профиле с кириллицей (`C:\Users\Максим`, локаль `Russian_Russia.1251`) это роняет инициализацию:

```
FATAL: invalid byte sequence for encoding "UTF8": 0xcc 0xe0
```

Причины две: путь к каталогу данных содержит не-ASCII символы и `initdb` наследует несовместимую с UTF-8 системную локаль. Тест обходит обе:

- каталог данных создаётся только в ASCII-пути без пробелов; `%TEMP%` под кириллическим профилем не используется;
- кластер пред-инициализируется вручную с явными `--locale=C --encoding=UTF8`, и уже готовый каталог передаётся в `pgserver` (шаг `initdb` пропускается);
- сбои `initdb`/запуска перехватываются и печатаются понятной диагностикой (код 3), без traceback;
- SQL передаётся в `psql` байтами в UTF-8 (не через `text=True`) с `PGCLIENTENCODING=UTF8`; stdout декодируется как UTF-8, stderr — с `errors='replace'`. Иначе на локали CP1251 stdin кодируется в cp1251 и падает на символах вне неё (например `↔` в комментариях `schema.sql`). Ошибки кодирования/декодирования дают понятное сообщение и ненулевой код, а не traceback.

Если стандартные ASCII-каталоги недоступны, путь задаётся явно:

```
set PG_TEST_TMPDIR=C:\pg_test_tmp   &  rem Windows
export PG_TEST_TMPDIR=/tmp/pg_test_tmp   # Linux/mac
```

Механика фикса проверена на Linux: полный прогон (кириллический контент сохраняется как UTF-8), отбраковка кириллического каталога и диагностика сбоя `initdb` — все ветки дают корректный код выхода без traceback. Финальную проверку на целевой Windows-машине с профилем `Максим` нужно выполнить командами из блока выше (ожидается строка `OK: ...` и код выхода 0).

## Статус

Схема и локальный конвейер сборки работают. Стартовый набор из десяти упражнений экспортируется из БД в мобильный каталог; сервер, API и удалённая публикация пока не поднимаются. Визуальная приёмка новых записей владельцем на телефоне выполняется отдельно от автоматического publication checklist.
