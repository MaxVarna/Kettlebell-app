# Рабочий фреймворк разработки продукта

Этот документ фиксирует единый способ развивать приложение: от пользовательской потребности до проверенной реализации. Он применяется к продуктовой логике, UX/UI, архитектуре и проверке результата.

## Каркас

**Outcome → Opportunity → Story Map → State → Slice → Learn**

В основе лежат четыре совместимые практики:

- **Continuous Discovery.** Начинаем с измеримого результата и реальной потребности, а не с заранее выбранного экрана или функции.
- **Dual Track.** Discovery и delivery идут параллельно: пока реализуется текущий вертикальный срез, уточняется следующий.
- **User Story Mapping.** Функции организуются по полному пути пользователя, а MVP выделяется как минимальный полезный проход через этот путь.
- **State-driven architecture.** Интерфейс отображает состояние; бизнес-правила и изменение данных находятся вне UI.

## Принципы

1. **Результат важнее списка функций.** У каждой инициативы есть один целевой пользовательский или продуктовый outcome и способ его измерить.
2. **Сначала путь, затем экран.** Экран не проектируется изолированно: он входит в пользовательский сценарий с понятным началом, действием, результатом и исключениями.
3. **Один вертикальный срез за раз.** В MVP функция проходит весь путь: данные → правила → состояние → UI → тест → измерение. Нельзя считать готовой только вёрстку или только доменную логику.
4. **UI не владеет бизнес-правилами.** UI отправляет намерения пользователя и отображает состояние. Правила тренировки, сохранение и восстановление живут в доменном и data-слоях.
5. **Все важные состояния спроектированы.** Для каждого потока определяются `loading`, `empty`, `ready`, `active`, `paused`, `error`, `offline`, `completed` — применимые к функции состояния.
6. **Решения обратимы, пока нет данных.** Гипотезы отделяются от подтверждённых фактов; рискованные допущения проверяются раньше дорогостоящей реализации.
7. **Системность UI важнее уникальности экранов.** Компоненты и дизайн-токены повторно используются; интерфейс сохраняет нативные ожидания Android и iOS.

## Цикл работы над функцией

### 1. Outcome

Формулируем один результат и его сигнал. Пример для первого MVP: «пользователь самостоятельно завершает первую тренировку и сохраняет её результат без необходимости разбираться в интерфейсе».

### 2. Opportunity

В Opportunity Solution Tree фиксируем:

- потребность или барьер пользователя;
- варианты решений;
- рискованные допущения каждого варианта;
- самый дешёвый способ проверить допущение.

В дерево попадают только наблюдаемые потребности, а не формулировки готовых решений.

### 3. Story Map

Размещаем решение на пользовательском пути и режем MVP по горизонтали: минимальный полезный сценарий прежде расширений и удобств.

Для runner-потока базовая карта выглядит так:

`выбрать тренировку → проверить план → начать → выполнить подход → отдохнуть → завершить → сохранить и увидеть итог`

### 4. Feature brief

До дизайна и кода для каждого среза создаётся короткий brief:

- задача пользователя и ожидаемый результат;
- основной UX-flow и альтернативные пути;
- сущности и бизнес-правила;
- события, которые меняют состояние;
- состояния UI и поведение при ошибке, паузе, офлайне и возврате в приложение;
- acceptance criteria;
- событие аналитики или иной способ оценить outcome.

### 5. UX/UI и контракт состояния

Дизайн создаётся вокруг flow и состояния, а не вокруг набора статичных макетов. Для каждого экрана фиксируются:

- входное `UI state`;
- доступные действия пользователя;
- ожидаемое новое состояние после каждого действия;
- контентные, пустые, ошибочные и доступные варианты;
- используемые дизайн-токены и повторно применяемые компоненты.

### 6. Delivery вертикального среза

Реализация следует направлению:

`намерение пользователя → use case / бизнес-правило → repository и источник истины → новое состояние → UI`

Для текущего технического контура это означает:

- UI-слой отображает состояние и передаёт события;
- data-слой хранит данные и отвечает за их согласованность;
- domain-слой добавляется только там, где правило сложно или используется несколькими экранами;
- у каждой сущности есть один источник истины;
- активная тренировка восстанавливается из сохранённого состояния, а не вычисляется по памяти UI.

### 7. Learn

После среза проверяем outcome и качественную обратную связь. Затем принимаем одно из решений: продолжить, улучшить, упростить или остановить гипотезу. Вывод возвращается в Opportunity Solution Tree и Story Map.

## Definition of Ready

Функцию можно брать в работу, только если есть:

- место на Story Map и границы MVP;
- feature brief;
- UX-flow;
- список состояний и исключений;
- acceptance criteria;
- понятный владелец источника истины для данных.

## Definition of Done

Вертикальный срез считается готовым, когда:

- реализованы доменные правила, хранение и UI;
- обработаны заявленные состояния и прерывания сценария;
- UX соответствует flow и использует дизайн-систему;
- добавлены пропорциональные тесты бизнес-правил и критического пути;
- outcome можно наблюдать или проверить;
- решение и открытые вопросы отражены в Story Map / журнале решений.

## Ритм

- **Перед началом среза:** уточнить outcome, opportunity и Story Map.
- **Во время delivery:** сохранять следующий срез в discovery, не расширять текущий без нового решения.
- **После завершения среза:** разбор результата и обновление карты, дерева возможностей и приоритетов.
